# Milo — 90 Day English Challenge

A local-first React Native app (Expo SDK 57, TypeScript strict, Expo Router), with an optional
backend in `server/` — the Milo API (NestJS, PostgreSQL, Prisma) for accounts and the course.
Without it the app runs exactly as before: the course bundled, all progress in SQLite on the
device. With it (`EXPO_PUBLIC_API_URL`), users sign in and the course comes from the API, cached
for offline play. Progress stays in SQLite either way — it does not sync yet.

## Data layer

- **Repositories** (`src/data/repositories`) are interfaces; the local implementations read bundled
  content and SQLite. `createDeviceServices` (`data/repositories/index.ts`) picks what a launch has
  once from the build's backend config — local only, or `ApiAuthRepository`, `ApiCourseRepository`
  and the progress API — and `repositoriesFor(device, owner)` opens one **owner's** progress: the
  device's own in local mode, an account's otherwise. No screen knows the difference.
- **Progress** belongs to an owner in SQLite (`owner_id` in every table) and, with an account, to
  the server: the phone keeps a projection and an outbox, synced by `ProgressSyncEngine` — see
  [Progress sync](#progress-sync).
- **The team** is the server's too (`ApiFriendsRepository`): the phone keeps its last answer per
  account (`team_cache`) for offline — see [Friends](#friends-team-challenge).
- **TanStack Query** owns all data access; `Zustand` only holds global client preferences
  (sound/haptics) and dev switches.
- **Zod** validates content, database rows and persisted settings; all domain types are `z.infer`.
- **Use cases** (`features/progress/use-cases.ts`) compose repositories: completing a quest awards
  XP once, evaluates achievements and returns everything a reward moment needs.
- **Writes are serialized** (`LocalStore.write`; `writeDatabase` in `data/db/database.ts`):
  exclusive transactions run on their own connection and SQLite rejects a second writer, so every
  write waits its turn — a double tap never fails with "database is locked", it finds the work
  already done. Repositories take the store as a `LocalStore`, so the same code runs on Node's
  SQLite in tests (`data/db/__fixtures__/node-sqlite-store.ts`).
- `queries.ts` inside each feature exposes the hooks; keys live in `data/query-keys.ts`.

## Backend (Milo API)

`server/` is a separate package (its own `package.json`, `node_modules` and lockfile) inside this
repository. The app was not moved into a monorepo: that would have been a large refactor for
nothing, since the server can use the app's code directly — `server/tsconfig.json` maps `@/…` to
`src/`, so the API compiles the app's own `src/schemas`, `src/content/course` and course validator.
There is one course and one set of schemas; `src/features/course/__tests__/shared-core.test.ts`
keeps that code free of React Native and Expo, so the server can keep compiling it.

**Stack:** Node 22+, NestJS 12, PostgreSQL 17, Prisma 7 (driver adapter `@prisma/adapter-pg`),
Zod (the shared schemas validate every request), argon2id, JWT (HS256) access tokens, pino logs,
Swagger, Vitest + supertest.

### Run it locally

```bash
npm run db:up                            # PostgreSQL 17 in Docker: milo + milo_test databases
cp server/.env.example server/.env       # then set the two secrets (command inside the file)
npm run api:install                      # dependencies + prisma generate
npm run db:migrate                       # migrations → the development database
npm run api:dev                          # http://localhost:3000
curl localhost:3000/ready                # {"status":"ready","checks":{"database":"up","course":"up"}}
```

Docker Compose runs one `postgres:17-alpine` service (`db`) with a named volume (`milo-pgdata`,
data survives restarts), a `pg_isready` healthcheck and port `5432` (`MILO_DB_PORT` to change it).
`server/docker/init-test-db.sql` creates the separate `milo_test` database on first start.

**Environment** (`server/.env`, validated at startup by `server/src/config/env.ts` — a missing or
unsafe value stops the API with a list of every problem):

| `DATABASE_URL`                  | — (required)                  | `postgresql://milo:milo@localhost:5432/milo?schema=public`                |

ignored; only `.env.example` is committed).

**Migrations.** Every schema change goes through `prisma migrate dev --name …` (`npm run
db:migrate` in development) and ships as SQL in `server/prisma/migrations/`; production runs
`npm --prefix server run db:deploy` (`prisma migrate deploy`). Never `db push`, never a manual
`ALTER TABLE`. There is no seed: the course is not in the database, and no users are invented —
tests create their own.

```bash
echo 'EXPO_PUBLIC_API_URL=http://localhost:3000/api/v1' > .env.local   # see .env.example

```

The iOS Simulator reaches the Mac as `localhost`; a physical phone needs the Mac's LAN address
(`http://192.168.x.x:3000/api/v1`). Without `EXPO_PUBLIC_API_URL` the app is in local mode — no

course bundled (content work without a server round trip).

### API (`/api/v1`)

|                                            |                                                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------ |
| `POST /auth/register`                      | `{ email, password }` → session (201). Credentials only: name and goal come from onboarding                  |
| `POST /auth/login`                         | `{ email, password }` → session. Unknown email and wrong password answer alike                               |
| `POST /auth/refresh`                       | `{ refreshToken }` → the next session (the token rotates)                                                    |
| `POST /auth/logout`                        | `{ refreshToken }` → 204; revokes that device's session. Idempotent                                          |
| `GET /auth/me`                             | the account (Bearer)                                                                                         |
| `GET /users/me`, `PATCH /users/me`         | the account; PATCH accepts only `displayName` and `goal`                                                     |
| `GET /course/current`                      | the manifest: `courseId`, `version`, `schemaVersion`, `contentHash`, `documentPath`                          |
| `GET /courses/:courseId/versions/:version` | the course document (ETag = its SHA-256, gzip, 304)                                                          |
| `GET /progress`                            | the account's progress and its revision (Bearer)                                                             |
| `POST /progress/sync`                      | offline mutations (≤ 50, in order) → one result each + the progress when it changed                          |
| `GET /teams/me`, `POST /teams`             | the user's team (or `null`); make one — see [docs/teams-and-invites.md](docs/teams-and-invites.md)           |
| `POST /teams/:teamId/invites`              | the team's open invite (members only)                                                                        |
| `DELETE /team-invites/:inviteId`           | turn an invite off (its maker or the owner)                                                                  |
| `POST /team-invites/preview`, `…/join`     | `{ code }` → the team before joining / join it (rate-limited per account)                                    |
| `POST /teams/:teamId/leave`                | leave; ownership passes on, the last member deletes the team                                                 |
| `PUT`, `DELETE /push/devices/current`      | team notifications on (`{ token, platform }`) / off for this device — see [docs](docs/push-notifications.md) |
| `POST /push/devices/unregister`            | `{ token }` → 204: a signed-out phone forgets its token (no account; rate-limited)                           |
| `GET /health` (outside `/api/v1`)          | alive; `{ status, database: "up" \| "down" }`                                                                |
| `GET /ready` (outside `/api/v1`)           | 200 when the database and the course are up, else 503                                                        |

A session is `{ user, accessToken, accessTokenExpiresAt, refreshToken, refreshTokenExpiresAt }`.
Every error is `{ code, message, details? }` with a stable `code` (`VALIDATION_ERROR`,
`EMAIL_TAKEN`, `INVALID_CREDENTIALS`, `UNAUTHORIZED`, `REFRESH_TOKEN_INVALID`,
`REFRESH_TOKEN_REUSED`, `NOT_FOUND`, `PAYLOAD_TOO_LARGE`, `RATE_LIMITED`, `COURSE_UNAVAILABLE`,
`COURSE_MISMATCH`, `COURSE_VERSION_UNSUPPORTED`, `ACCOUNT_MISMATCH`, `FORBIDDEN`,
`CHALLENGE_NOT_STARTED`, `ALREADY_IN_TEAM`, `ALREADY_MEMBER`, `TEAM_FULL`, `TEAM_NOT_FOUND`,
`INVITE_INVALID`, `INVITE_EXPIRED`, `INVITE_REVOKED`, `INTERNAL_ERROR`) — never a stack trace. Validation errors list `details: [{ path, message }]`.

**Swagger** (development and staging): http://localhost:3000/api/docs, JSON at
`/api/docs/openapi.json`. It is generated from the same Zod schemas the API validates with, so it
cannot drift from the real DTOs.

### How auth works

- **Passwords:** argon2id (19 MiB, 2 passes, 1 lane — OWASP's baseline): memory-hard, so stolen
  hashes stay expensive to guess on GPUs. Parameters live in each hash; stronger ones rehash at the
  next sign-in. An unknown email is checked against a decoy hash, so timing does not reveal
  which emails exist.
- **Access token:** a JWT (HS256, 15 minutes by config) naming the user and the session. The guard
  also checks that the session is still active, so logout and a detected replay cut access at
  once, not when the token expires.
- **Refresh token:** 256 random bits, opaque; the database keeps only its HMAC-SHA256
  (`refresh_tokens.tokenHash`). A session (`refresh_sessions`) is one signed-in device. Tokens are
  single-use: each refresh returns the next one and records which token it replaced
  (`parentId`). A used token presented again is a replay — someone has a copy — and revokes the
  whole session (`REFRESH_TOKEN_REUSED`). The one exception is a retry: the same token within
  `REFRESH_TOKEN_REUSE_GRACE` while nothing issued for it has been used (a response lost on a bad
  network) gets a successor of its own; whichever successor is used first retires the others.
  Refreshes of one session are serialized with a row lock, so races cannot fork a session.
- **Rate limits:** sign-up and sign-in, per client address and route (429 with `Retry-After`,
  `AUTH_RATE_LIMIT`); team invite previews and joins, per account (`INVITE_RATE_LIMIT`). Refresh
  and logout take an unguessable token: nothing to guess there.

### Security and logging

Helmet headers, CORS closed unless origins are listed, JSON bodies limited to 100 kB (413; 1 MB
for progress sync, which may carry a phone's history once), every
request validated by the shared Zod schemas (unknown fields are refused), production-safe errors.
Logs are one JSON line per request (pino): request id (`X-Request-Id`, echoed back), method, path,
route pattern, status and duration. Headers and bodies are never logged — no passwords, no
tokens — and a redaction list guards error objects; `test/logging.test.ts` checks it.

## Accounts in the app (API mode)

- **Auth states:** `bootstrapping` → `authenticated` / `unauthenticated` (`stores/auth-store.ts`).
  The splash screen stays up until the Keychain has been read, so a signed-in user never sees the
  sign-in screen flash. Routes are guarded in `app/_layout.tsx`: signed out → sign in / sign up;
  signed in and new → onboarding; signed in and onboarded → the challenge. In local mode the
  device is always signed in.
- **Tokens** live in the Keychain (`expo-secure-store`, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`:
  never in a backup, never on another phone), never in AsyncStorage, SQLite or the HTTP cache.
  Verified in Milo's own iOS development build (`npx expo run:ios`): after sign-up, refreshes,
  logout and login, a scan of the app's whole sandbox finds no access or refresh token; the URL
  cache (`Library/Caches/<bundle id>/Cache.db`) holds only the two course requests.
- **Expo Go only (development):** Expo Go keeps responses in _its own_ URL cache — auth responses
  and their tokens included — despite the API's `Cache-Control: no-store`. That is Expo Go's
  sandbox, not Milo's, and Milo's own builds do not do it (their URL cache honours `no-store`).
  Check anything about networking or storage in a development build, not in Expo Go.
- **One API client** (`services/api/api-client.ts`): base URL, JSON, the Bearer token, a timeout,
  errors as `ApiError` (`code` from the API, or `NETWORK_ERROR` / `TIMEOUT` / `BAD_RESPONSE`).
  A 401 refreshes the token and retries the request once. Refreshing is single-flight: five
  requests refused at once share one refresh; if the server refuses the refresh, the session is
  cleared once and the app signs out once. Offline is not signed out: nothing is cleared.
- **Sign in / sign up** (`features/auth`): React Hook Form with the API's own schemas. Sign-up asks
  only for email and password (+ confirmation); the name and the goal stay in onboarding, which
  comes next — never asked twice. Signing in on a new phone prefills onboarding from the account.
  When onboarding finishes, the name and goal go to the account (best effort).
- **Existing local users:** nothing on the device is deleted by signing up, in or out. The
  progress a phone has from before accounts goes, once, to the first account signed in there if
  that account has no progress anywhere — it lands straight back in its challenge, sent to the
  server as its history (see [Progress sync](#progress-sync)); an account that already has progress
  never gets another history merged in.
- **Logging out** (Settings → Account): stops the account's sync, revokes the session on the server
  (best effort — it also works offline), clears the Keychain and drops the account's screens and
  cache. The account's progress stays on the phone, out of sight, until it signs in again.

### The course from the API

`ApiCourseRepository` implements the same `CourseRepository` as `LocalCourseRepository` (they share
`CourseReader`): API → hash check → JSON → full validation → SQLite cache (`course_cache`,
migration 11) → gameplay. The course in use is chosen once per launch without the network: the
saved download if it is still valid (and not older than the app's bundled course), otherwise the
bundled course. In the background the app checks the small manifest; a new `version` or
`contentHash` downloads the document, which must match the hash, parse, pass `validateCourse` and
be the course the manifest announced — then it is saved and used from the next launch, never
under a running game. Broken JSON, an invalid course or an unsupported `schemaVersion` are refused
with a logged warning, and the last known good course stays exactly as it was.

## Progress sync

Progress is the account's, and the server owns it; the phone keeps a projection and an outbox
(architecture, rules and limits: [`docs/progress-sync.md`](docs/progress-sync.md)).

- **Actions, not results:** starting the challenge, a quest's answers, an exam's answers go to the
  server as mutations (`src/schemas/progress-sync.ts`); the server scores them against the course
  and derives XP (an append-only ledger), days, streaks and badges with the app's own rules.
- **Offline first:** a quest counts on the phone at once — its progress and its outbox entry are
  one SQLite transaction — and survives restarts. `ProgressSyncEngine` sends the outbox when the
  account opens, a change is stored, the app returns to the foreground or the connection comes
  back: single-flight, 50 per request, in order, exponential backoff, no polling.
- **Idempotent:** every mutation has a UUID; the server records each outcome with its effects, so a
  retry is a `duplicate` and changes nothing; rewards, days and badges are unique in PostgreSQL.
- **Accounts on one phone:** every progress table is scoped by owner; each account gets its own
  repositories, query cache and sync; another account never sees a row of it, and its outbox is
  only ever sent as that account.
- **Revision:** the server's revision goes up with every change; the phone sends the one it has and
  gets the progress back only when it moved.

## Assets

`src/constants/assets/registry.generated.ts` is generated from `assets-manifest.json` — the app
never calls `require()` for an asset directly:

```ts
import { mascots, badges, quests, sounds } from '@/constants/assets';

<AssetImage asset={mascots.idle} width={120} />;
playSound('questComplete');
```

Each entry carries intrinsic size, alpha and the review status from `ASSET_MANIFEST.md`.
Missing assets are listed in `missingAssets` (currently `quest-grammar.svg`).

Sprite sheets are cut into separate originals by `npm run assets:slice` (rects live in
`assets.config.mjs → slices`), then optimised like any other original. The flag sheet
`journey-flag` is only a reference: use `journey.flagNormal`, `flagCheckpoint`, `flagComplete`,
`flagLocked`, `flagBanner`, `flagSmall`, `flagString` or `flagLarge` — each base sits on the
image's bottom edge, so a flag anchors bottom-centre.

`assets-native/` holds the few images the native build reads at prebuild (config plugins), never
the JS bundle — outside the pipeline's `assets/`. `android-splash-icon.png` is transparent on
purpose: Android's splash theme needs an icon drawable, and Milo's splash is its background colour
alone, as on iOS, until there is splash artwork.

## Sound & haptics

- `playSound('correct')` — one reusable player per sound, created once; respects the iOS silent

- `triggerHaptic('questComplete')` — semantic patterns, subtle by default.
- `playFeedback('dayComplete')` — the sound + haptic pair for one app moment (single source of truth).

## Onboarding / first launch

`src/features/onboarding`: six short steps, each with its own composition — **Meet Milo** (the
mascot, "Let's go"), **the journey** (90 days, camp → forest → river → mountains → summit),
**a day** (Day 1's real quests and time, the streak, badges and friends), **the goal**,
**the name**, and **Ready** (Chapter 01, "Start Day 1"). No global skip. Onboarding itself never
asks for an account: in API mode the account is made just before it (email and password only),
and onboarding keeps asking the name and goal — prefilled when the account already knows them.

- **Routing** is a guard, not a redirect: `app/_layout.tsx` wraps the app's routes in
  `<Stack.Protected guard={signedIn && onboarded}>` and onboarding in
  `<Stack.Protected guard={signedIn && !onboarded}>` (sign-in and sign-up are behind `!signedIn`,
  and in local mode the device is always signed in), so a profile that
  never finished onboarding can reach nothing else, and the moment the challenge starts
  onboarding is gone — no back gesture, no deep link (`/onboarding`) leads back into it. The first
  decision uses the profile `useAppBootstrap` already loaded, so nothing flashes.
- **The profile** (migration v9) gains `goal` and `onboarded_at`. `onboarded_at IS NULL` is what
  "new" means; the migration stamps every existing profile as onboarded, so a user on Day 89 is
  never sent back to the start.
- **Starting the challenge** is one domain operation — `startChallenge`
  (`features/onboarding/use-cases.ts`) — and it is idempotent: the write only touches a profile
  that is still new (`WHERE onboarded_at IS NULL`), so a double tap, a retry after an error or a
  second launch can never restart the challenge or move Day 1. Day 1 is simply today; completed
  days, streak, XP and Chapter 01 follow from an empty history and need no rows of their own.
- **The draft** (`stores/onboarding-store.ts`, AsyncStorage, validated on load like the settings)
  keeps the step and answers between launches: closing the app halfway through comes back to the
  same step. Finishing clears it.
- The day step reads Day 1's plan (`useCourseDay(1)`): quest names, count and "about 20 min"
  come from the course, never from copy. The keyboard lifts the footer (`useAnimatedKeyboard`)
  and goes away on a tap or a drag; the name is validated live against the same
  `DisplayNameSchema` the repository parses. Start Day 1 is the only sound in the flow
  (`challengeStart`: a soft tap and a success haptic).
- Dev fixtures cannot become a production path: `features/dev-tools/__tests__/dev-boundary.test.ts`
  fails if anything but the dev tools route and the dev-only settings group imports them, or if
  the in-memory test repositories reach the app.

## Home / Today

`src/features/today`: the daily entry point. Data comes from `useTodayJourney()` (repositories →
`loadTodayJourney` → pure `buildTodayJourney`), never from hardcoded arrays.

- Quests form one route: done → current (available / in progress) → locked, ending at camp.
  "In progress" is a row in `quest_sessions` (migration v2) without a completion.
- `useJourneyMoments` compares what Home saw last with the new data while Home is on screen:
  a finished quest, a completed day or a longer streak becomes one moment with its sound, haptic
  and animation. Reopening the app shows the finished state without replaying anything.
- A complete day shows a calm finished state: 4 of 4, the lit camp with "Tomorrow: Day 90 ·
  Summit" (tap it for the day's summary), a quiet "A perfect day" line when every answer was right.
  A day celebrated on its Day Complete screen is never celebrated again on Home.

## Quests

Every quest opens `app/quest/[questId].tsx`; `QuestScreen` picks the gameplay by quest type.
Vocabulary, Grammar, Reading and Review share one engine instead of four:

- `features/quests/hooks/use-quest-flow.ts` — runs a quest through its type's reducer, saves the
  position after every step (`quest_sessions.state_json`, so a quest resumes where it was left),
  finishes it once through `completeQuest` (XP once per quest, guarded by a unique index).
- `features/quests/logic/practice.ts` — shared choice logic: the first answer is locked in,
  "Continue" only after an answer, scoring, validation of saved answers against the content.
- Shared components: `QuestTopBar`, `QuestIntro`, `ChoiceQuestion`, `AnswerFeedback`,
  `QuestResult`, `QuestCompleted` (reopening a finished quest, XP-free "Practice again").

Each quest type owns only its content schema (`schemas/`), a small reducer (`logic/*-session.ts`)
and its own views. The **Review** (`features/review`) adds no new material: its exercises refer to
words, grammar rule points and stories by their course ids — from that day or any day before — and
the resolved quest carries exactly that material (`material`); `resolveReview` builds the mixed
exercises from it and reuses the quests' prompt components (`VocabularyPrompt`, `GrammarPrompt`,
`ReadingPrompt`).

## Course content (the 90-day course)

The whole course is one plain, serializable document (`Course`, `schemas/course.ts`) — exactly what
an API would send later. The app never decides what a day is from its number: a day's kind, week,
chapter, level and quests all come from the course.

```
src/content/course/
  meta.ts             id "milo-english-90", version, title, language "en", support language "ru", 90 days
  chapters.ts         the five chapters: day ranges, band on the difficulty curve, purpose
  plan.ts             the 90 course days: kind (regular · weeklyExam · summit), week, chapter,
                      CEFR level (from the chapter's band), quest slots with XP and minutes
  curriculum/         the learning design: bands, grammar syllabus, theme families, outcomes,
                      one draft per day (days/chapter-0N.ts, summit.ts), attached to each day
  days/day-NNN.ts     a written day: its new words, grammar lesson, reading text and quest definitions
  checkpoints/        weekly exams (week-NN.ts)
  final-challenge.ts  the Final Battle
  index.ts            LOCAL_COURSE — assembled from the files above
  __fixtures__/       test-only helpers (never imported by the app)
```

- **Normalized banks, lessons by reference.** Words (`vocabulary`), grammar lessons (`grammar`) and
  texts (`readings`) are banks keyed by id; a day's quests (`lessons`) only reference them —
  a Vocabulary quest lists `wordIds`, a Grammar quest a `lessonId`, a Reading quest a `readingId`,
  a Review quest exercises that point at words, rule points and texts taught earlier. A reading
  gloss can point at the vocabulary bank (`vocabularyId`) instead of repeating the word.
- **Stable ids, one convention** (`features/course/logic/ids.ts`): days `d001`, quests
  `d001-vocabulary`, words `vocab-<lemma>`, grammar `grammar-<topic>` with points
  `<lessonId>.<point>`, texts `reading-<slug>`, exams `exam-week-01` and `final-challenge`.
  Progress stores only ids (learned words by word id, completions by quest id), so fixing a typo
  or rewriting an exercise never breaks it. An id, once shipped, is never reused for other material.
- **Versioned.** `version` goes up when content changes in a way progress should know about;
  every quest completion and exam attempt records the `courseVersion` it was earned on
  (migration v10, which also renamed the pre-convention word ids: `journey` → `vocab-journey`).
- **Resolved for gameplay.** `resolveQuestContent` (`features/course/logic/resolve.ts`) turns a
  quest definition into the content models the four quests and the exams already play
  (`QuestContent`) — gameplay did not change.
- **Validated before use.** `validateCourse` (`features/course/logic/validate.ts`) runs Zod on every
  entity, then the rules across the course, and names each problem by id
  (`d002-review.exercises[0].itemId: word "vocab-proud" is taught on d007, after d002`): unique ids
  and their conventions; the plan (90 days, in order, none missing or doubled; chapters back to
  back; each day in its chapter; one summit on the last day, the Final Battle alone; checkpoint days
  end with their exam; levels never go down); every reference resolves; material is taught once and
  reviewed or tested only after it was taught; material fits its day's level; exam rewards, days
  and weeks match their quests; every quest resolves into playable content. Unwritten material
  covered by an exam is a warning, not an error.
- **Repository.** `CourseRepository` (`data/repositories/types.ts`) is async; `LocalCourseRepository`
  validates the bundled course once and refuses to serve an invalid one. An `ApiCourseRepository`
  will validate a downloaded course the same way and keep it for offline play — no screen changes.
  Query keys: `queryKeys.course.*`, `staleTime: Infinity` (content, not progress).
- **Content status.** `npm run content:validate` prints what is written (`CONTENT STATUS: PARTIAL`
  until every quest of every day has content) and exits non-zero on any error; `npm test` checks
  the same course. Written now, as a representative slice: Days 1, 2, 7 (the first checkpoint),
  89, the Week 1 and Week 12 exams and the Final Battle. Every other day is planned (kind, level,
  quests, rewards); a quest without content opens as "not ready yet" (`QuestUnavailable`).

Adding a day: read its row in [docs/CURRICULUM_90_DAY.md](docs/CURRICULUM_90_DAY.md), write
`days/day-NNN.ts` (new words, lesson, text, quest definitions whose ids follow the convention), add
it to `WRITTEN_DAYS` in `index.ts`, run `npm run content:validate`.

### Curriculum (the 90-day blueprint)

What every day should teach, as data: `CourseDay.curriculum` (theme, vocabulary focus with anchor
words, grammar topic and stage, reading genre/topic/skills/length, review mix and days — or a
checkpoint's exam objectives, or the Final Battle's blueprint) and `Course.curriculum` (difficulty
bands, a 32-topic grammar syllabus with prerequisites, 26 theme families, learning outcomes). The
drafts in `content/course/curriculum/` hold only what a person decides; the build works out the
rest from the course plan (text length from the band, review days by spaced repetition, what a
weekly exam covers — never from `day % 7`).

`validateCurriculum` (`features/course/logic/curriculum.ts`) runs in `content:validate` and the
tests — not at app startup. Errors: a day without objectives or of another kind than the plan's, a
topic before its prerequisites or practised before it is introduced, a theme family twice in a row,
an anchor word planned twice or already taught, a review that does not add up or comes back to a
later day, a checkpoint not covering exactly the days since the previous one, a Final Battle
blueprint that does not add up, a band that goes down, a chapter without an outcome. Warnings:
written content that drifted from the plan (reading length, question kinds, review days, exam
coverage and balance). Days whose written content no longer fits carry a `revision` note and show
as NEEDS_CONTENT_REVISION.

The human-readable version, with the strategy, the day-by-day map and the audit, is
[docs/CURRICULUM_90_DAY.md](docs/CURRICULUM_90_DAY.md); its generated sections come from the same
data (`npm run curriculum:doc`, kept in sync by a test).

## Exams (weekly checkpoints and the Final Battle)

`src/features/exams`: one engine for both — a weekly exam on every checkpoint day of the course
plan and the Final Battle on Day 90 (`schemas/exam.ts`, `content/course/checkpoints/`,
`content/course/final-challenge.ts`). `ExamScreen` renders both; only the wording and what a pass
finishes differ (`Flavor`).

- No instant feedback: an answer can be changed until the exam is submitted, "Previous" / "Next"
  walk the questions, progress reads "12 / 20". The attempt is saved after every answer
  (`exam_attempts`, migration v7), so a force close resumes where it stopped; submitting with
  unanswered questions asks first.
- **Submission is one exclusive transaction**: the attempt is marked submitted only if it was not
  (`WHERE submitted_at IS NULL`), XP is paid once (a unique partial index), the quest completion,
  the answers, the day record and — for the Final Battle — the challenge completion are written
  together. A double tap or a retake pays nothing twice.
- Pass mark comes from the exam definition (70%), not the UI. A failed attempt finishes nothing:
  "You're close." with the mistakes to review and a retake.

## Day complete

- A day is complete when all of its quests are — decided by `completeDay`
  (`features/progress/use-cases.ts`), never by a screen. The last quest's completion records it
  once in `day_completions` (migration v4, primary key = day): XP earned (bonuses included),
  streak before → after, perfect or not. Calling it again (double tap, "Finish Day", a re-render)
  returns the same record; wrong answers never block it.
- The Review result leads to **Finish Day N** → `app/day-complete/[day].tsx`: Milo at the lit camp,
  "Day N complete", quests resolving to 4/4, XP counting up, the streak stepping up, a light
  confetti sweep — about 2.5 s, skippable with a tap. One sound (`day-complete`), the streak step is
  haptic only; Reduce Motion shows the final state at once, haptics follow the user's setting.
- The celebration plays once, ever: the screen claims it (`celebrated_at`, an atomic update) and
  reopening the day — from Home's camp, after a restart — shows the same summary quietly. If the
  user leaves the result without "Finish Day", Home celebrates instead and claims it the same way.

## Journey (90-day map)

`src/features/journey`: the whole challenge as one trail, from the base camp (bottom) to the
summit (top). It adds no progress of its own:

- `buildJourney` (`logic/journey.ts`, Zod: `schemas/journey.ts`) derives every day's state
  from the challenge state — `completed`, `available` (today), `missed` (passed without its
  quests), `locked` — its kind (`weeklyExam`, `chapterEnd`, `summit`) and stored facts only
  (XP, date, perfect) from `day_completions` or the quest completions.
- `buildMapLayout` (`logic/map-layout.ts`) turns it into geometry for the screen width: days on
  a sine wave (one swing every 8 days), a gate per chapter (its illustration), one scenery
  illustration per chapter where the trail swings away, flags at chapter ends, Milo and today's
  campfire beside today's node. Tests check that nothing overlaps at 320–440 pt, on every day.
- Rendering stays light: the trail is small views (solid behind today, dotted ahead) — no tall
  canvas; only what lies within ~1.5 screens of the viewport is mounted.
- The map opens on today (or where the user left it this session), follows a new day, and a
  node opens the day's details; today's CTA leads to Home — the map never starts gameplay.

## Summit (Day 90)

`src/features/summit`: the finale. Day 90 opens as a scene (`SummitIntro`) instead of a quest list,
the Final Battle mixes the whole challenge, and passing it settles everything at once.

- The completion transaction (see Exams) records the Final Battle, Day 90 and the challenge
  itself; `syncAchievements` then unlocks the 90-day badge through the same engine as any other.
- `SummitScreen` plays the victory once, ever: the first visit claims the moment — the challenge,
  Day 90's summary and every badge it shows — so nothing stacks afterwards. Every later visit
  (`/summit?replay=1` from the map, a reopened app) shows the summit at rest and pays nothing.
- Home becomes `ChallengeComplete`: there is no Day 91, no "0 of 4" — the journey, 90/90, the
  streak and total XP, and the ways back into it.

## Achievements

`src/features/achievements`: the 12 badges (`data/content/achievements.ts`), each with one rule
(`schemas/achievement.ts`) — First Day (1 completed day), 3/7/14/30/50-day streaks (days in a row),
90 Days (all 90), 100/500 words (unique word ids in `learned_words`, migration v5), Perfect Quiz
(a scored quest without a mistake), Perfect Week (7 perfect days in a row), Team Streak (7 team
days in a row — granted by the server only, see [docs/teams-and-invites.md](docs/teams-and-invites.md)).

- `buildAchievementFacts` derives what the rules need from stored progress; `evaluateAchievements`
  turns facts + unlocks into `locked` (with real progress) / `unlocked` / `notAvailable`.
- `syncAchievements` runs after every quest completion (after the day is recorded): the
  repository unlocks atomically, XP is paid once, the result is the "newly unlocked" event.
  A persisted unlock never locks again.
- Celebrations: unlocks are stored with `celebrated_at = null`; `AchievementCelebrationHost`
  shows them only on the tabs (never over a quest, a result or Day Complete), one card for
  everything unlocked together ("+4 more achievements"), and claims them as it shows them.
- `/achievements` (from Profile → "See all"): the collection by category, badge details in a sheet.

## Friends (team challenge)

`src/features/friends`: a team of up to three friends taking the same challenge — not a social
network. The Milo API keeps it; rules, invites, the team streak, privacy and offline behaviour are
in [`docs/teams-and-invites.md`](docs/teams-and-invites.md).

- Models (`schemas/team.ts`): `TeamSnapshot` (members as `TeamMemberSummary` — day, today, streak,
  XP, never email, answers or history — the team streak, the open invite), `InvitePreview`,
  `TEAM_CAPACITY` (3), invite codes (`7K2PX-9QDMA`, 50 bits) and links (`milo://invite/<code>`).
- `FriendsRepository`: `ApiFriendsRepository` with an account (the server's answers, kept per
  account in `team_cache`), `LocalFriendsRepository` in local mode (no server: the dev tools' demo
  team, changes refused). The user's own card is their local progress, so it moves at once.
- Friends tab: no team (Create team / Join with a code), 1/3 with the code to share, 2/3, 3/3
  (full), the last team offline with a note, **Internet connection required** for every change.
  The invite page (`app/invite/[code].tsx`) shows the team before joining; an invite opened
  signed out or before onboarding waits and opens afterwards (`PendingInviteWatcher`).
- Team streak: computed by the server from its day records (`logic/team-streak.ts`, shared) — a
  date counts when every member who had joined by then finished their day, two or more members.
  It unlocks the Team Streak badge (7 in a row) on the server, once per member.
- Member statuses ("Done", "Almost there"…) and the words ("One more to go") are derived on the
  phone, never stored; the team is named, never a person.
- **Team notifications** (Android): a teammate joins or finishes today, your turn, the team day
  complete, streak milestones — sent by the server through Expo and FCM, one per person per action.
  See [`docs/push-notifications.md`](docs/push-notifications.md).

## Profile & Settings

- Profile (`features/profile`) is a projection: `useProfile` selects from the queries other screens
  already use (progress, achievements, team, user) through the pure `buildProfileView` — streak,
  total XP, days, unique words, the journey, the latest unlocked badges, the team in one line.
- Settings show only settings that work: sound effects and haptics (`stores/settings-store.ts`,
  persisted, every field validated on load by `parseSettings` — a corrupted value falls back to
  its default), the system Reduce Motion state (the app follows it; no duplicate toggle), the
  display name, the challenge start date, About with the version from `app.json`. The developer
  group (dev tools, reset with confirmation) exists only in `__DEV__` builds. With an account
  (API mode), an Account group comes first: who is signed in, and Log out — and, on Android builds
  of Milo, a Team group: **Team notifications** (`features/push`), on only after the permission
  flow and the server's registration.
- `SoundManager.play` and `triggerHaptic` read the preferences centrally — no screen checks them.

## Daily reminders

`src/features/reminders` + `src/services/notifications`: one gentle local notification a day at
a time the user picks — no push, no server, no account.

- **Preference** lives in the existing settings store (`dailyReminderEnabled`,
  `dailyReminderTime`, Zod-validated field by field; a broken stored time falls back to 19:00).
  Off by default. Permission is asked only when the user switches the reminder on in
  Settings → Reminders, after a one-sentence explanation; a refusal leaves the switch off, and a
  permanent one offers "Open Settings" (`Linking.openSettings`). If the permission is later taken
  away in iOS Settings, the preference follows it on the next return to the app.
- **Scheduling** is one reconcile operation, `syncDailyReminders`: `planReminders` works out the
  reminders that should be waiting — one per date for the next 14 days, id
  `milo.daily-reminder.YYYY-MM-DD` — and the service cancels what is stale, schedules what is
  missing and leaves the rest. Per-date ids make duplicates impossible; syncs are serialized;
  platform failures are caught, counted and retried on the next sync, never thrown.
- **What the plan knows**: nothing while off, not permitted, during onboarding or after the
  summit (90/90); nothing today once today's day is complete (the next reminder is tomorrow's,
  worded for the next challenge day), nor once today's time has passed. A delivered reminder
  leaves Notification Center once its day is done.
- **When it runs**: `ReminderSync` (mounted in the root layout, renders nothing) follows the
  preference, onboarding, the current day, "today complete" and the challenge completion, and
  syncs on every change — whatever caused it — and whenever the app returns to the foreground.
  Gameplay code never calls reminders.
- **Time zones**: iOS triggers are calendar components without a zone, so 19:00 stays 19:00
  after a flight; Android fixes the instant, so each reminder carries its UTC offset and is
  planned again when the offset changes (a flight, a DST switch) on the next sync.
- **Words** live in `features/reminders/copy.ts`: gentle, never about losing a streak;
  checkpoint days and Day 90 get their own.
- **Tap** opens Today (`/`) — the completed Home after the summit. While the app is open, a daily
  reminder stays silent.
- The daily reminder is **local** and stays that way: no server, no push token, no network. Team
  notifications are server pushes, apart (`features/push`, [docs](docs/push-notifications.md));
  the two share only the permission. The `expo-notifications` plugin in `app.json` sets the
  Android notification color and the push channel; Expo Go still runs the reminder on iOS.

## Conventions

- No hardcoded colors, spacing or typography — use `@/theme` tokens.
- Screens stay thin: data via queries, logic in `logic/` or `use-cases.ts`.
- No custom native code: configuration only through `app.json` / `app.config.ts` plugins. The app
  runs in Expo Go (`npx expo start --go`) except team notifications, which need a development
  build (`eas build -p android --profile development`).
- Expo SDK 57 changed a lot: check https://docs.expo.dev/versions/v57.0.0/ before using an API.
